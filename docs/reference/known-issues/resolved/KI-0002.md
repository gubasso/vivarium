# KI-0002 — a guest half-close never reached the host peer

- Status: `resolved` on 2026-08-10.
- Severity: high — the credential relay stopped serving after `CREDENTIAL_POOL_SIZE` clients for the life of the VM.
- External system: Cloud Hypervisor, defective through v52.0, fixed in v53.0.
- Affected checks: `guest agent lane` in [`../../../../tests/host/guest-agent-check`](../../../../tests/host/guest-agent-check), specifically `credential_relay_survives_pool_depletion`.
- Mask: none, at any point. The case was found and closed by a pin move, so nothing in vivarium ever suppressed or expected the failure.

## Symptom

The parked credential pool served exactly four clients and then served no more. Measured on a live guest at v52.0: one client succeeded, then three of four, then none of six. The guest's view while wedged was fourteen connections queued on the accept backlog of `/run/vivarium/ssh-agent.sock` against four vsock connections on port `52001` sitting `ESTAB` with empty queues.

## Root cause

Cloud Hypervisor v52.0 handled a guest `VSOCK_OP_SHUTDOWN` by recording `ConnState::PeerClosed(recv_off, send_off)` and nothing more. The write half of the backing host Unix socket was never shut down, so the host peer never read end of file. Both ends of the relay then waited for the other forever: [`tokio::io::copy_bidirectional`](https://docs.rs/tokio/1.53.1/tokio/io/fn.copy_bidirectional.html) completes only once both directions have shut down, so neither `serve_local` in `crates/vivarium-guest-agent/src/credentials.rs` nor `worker` in `src/launch/credentials.rs` could return, and the worker never looped back to `establish()` to refill the slot.

vivarium's own code was correct against a conforming transport, and no vivarium code was written to close this case. The hazard class is well known in tokio proxies: [tokio#3876](https://github.com/tokio-rs/tokio/issues/3876) and [shadowsocks-rust#1195](https://github.com/shadowsocks/shadowsocks-rust/issues/1195) are the same shape.

See the pinned [v52.0 `csm/connection.rs`](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v52.0/virtio-devices/src/vsock/csm/connection.rs).

## Deployed fix and proof

[PR #8372](https://github.com/cloud-hypervisor/cloud-hypervisor/pull/8372), in its own words fixing that "the write half of the host Unix socket was never closed so the host peer never saw an EOF", merged 2026-06-12 and shipped in v53.0. At [v53.0 `csm/connection.rs`](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v53.0/virtio-devices/src/vsock/csm/connection.rs) the guest's send-side half-close reaches the host socket through `shutdown_host_write_side`, which issues `libc::shutdown(fd, SHUT_WR)`.

vivarium adopted it by advancing the `nixpkgs` pin in [`../../../../nix/flake.lock`](../../../../nix/flake.lock) to `f13ff45afd1bb73e640eaa08a7066dbed07e3238`, which carries cloud-hypervisor 53.0.

The proof is the pair of observations, not the reading. At v52.0 the lane failed with the pool wedged; at v53.0, with the product tree otherwise untouched, `credential_relay_survives_pool_depletion` drives six concurrent clients through four slots for twenty rounds and passes. Recorded twice on 2026-08-10 in [`../../microvm-verification-harness.md`](../../microvm-verification-harness.md).

## Recurrence signal

`tests/host/guest-agent-check` is the signal, and it needs no separate probe: `credential_relay_survives_pool_depletion` uses more concurrent clients than the pool has slots, so it cannot pass without a refill, and a refill cannot happen without the half-close. A pin move that regressed below v53.0 would fail that assertion directly.

The backend pin MUST therefore stay at or above cloud-hypervisor v53.0. [`../../backend-capabilities.md`](../../backend-capabilities.md) owns that constraint as a capability fact.
