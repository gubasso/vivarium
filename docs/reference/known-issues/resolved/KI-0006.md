# KI-0006 — the spectrum git host did not answer, and a cold fetch of it hung the suite

- Status: `resolved` on 2026-11-22.
- Severity: medium. Every CI lane that ran `viv` hung on a cold runner, and a fetch that hangs fails no check by itself.
- External system: the git host `spectrum-os.org`, reached through the `spectrum` input of microvm.nix, which [`nix/flake.lock`](../../../../nix/flake.lock) locks as a `git` input.
- Affected checks: the `test-local` and `test-eval` lanes on a GitHub runner, first seen in run 44750215556 on 2026-11-20.
- Mask: none.

## Symptom

On 2026-11-20 every `local_workflows` trial that ran `viv` timed out at its 120 s `slow-timeout`, and three `eval_workflows` trials timed out at 360 s. The same trunk commit had passed on 2026-11-12.

## Root cause

The suite pinned the two baseline inputs through `nix flake archive` over the product flake, and that command fetches every input of the lock recursively, `spectrum` among them. spectrum-os.org accepted no TCP connection, and a git fetch has no timeout of its own, so on a cold store each trial blocked until nextest killed it. A stopgap bounded the fetch of the two baseline inputs with a deadline.

## Deployed fix and proof

The binary ships the first pin ([`ADR-0116`](../../../decisions/ADR-0116-the-binary-ships-the-first-pin.md)). A pre-flight writes `nix/flake.lock` as a target's first lock through Nix's lock step, which keeps every node of the reference and downloads nothing for it. The suite takes that path from a fresh data root, so it runs no archive and needs no deadline, and the stopgap is gone.

The one-time cold-store verification of 2026-11-22 evaluated the shipped `rust-web` example on an empty store and cache. It exited `0`, and the store held no path with the `spectrum` `narHash`: the tested cold evaluation did not materialize `spectrum`. The [findings register](../../microvm-verification-harness.md) owns the command and the observations.

## Recurrence signal

A target whose selected image carries a base flake that declares `microvm` without a `flake.lock` still resolves `spectrum` live at its first lock, because the shipped pin holds no node under a base. That lock step contacted spectrum-os.org during the verification, and a host outage would block it. A first lock that hangs with a base flake in force is this case returning, and the decision about it belongs to the product.
