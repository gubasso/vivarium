# 08 — Invariants and guarantees

The normative rules the product must uphold. Each is a guarantee callers and reviewers may rely on; changing runtime, build, or composition behavior must preserve them. Each invariant links to the page or decision that explains it. The keyword MUST marks a hard requirement.

## Isolation

- N1 — Separate-kernel boundary. A workspace MUST run behind a hardware-virtualization boundary with its own guest kernel; there is no shared-kernel mode. See [`../../decisions/ADR-0001-microvm-isolation-boundary.md`](../../decisions/ADR-0001-microvm-isolation-boundary.md).
- N2 — Class, not tool. The isolation boundary MUST be specified by capability class, not by a named virtual machine monitor. Any backend satisfying the class is admissible; none is part of the contract.
- N20 — VMM and host-daemon sandbox. The virtual-machine-monitor process MUST be launched under a host-side sandbox — a seccomp syscall filter plus capability drop — so that even a compromised VMM cannot reach the host beyond its sanctioned resources. The same standard applies to every host-side helper daemon that processes guest-controlled data, notably the shared-filesystem daemon (virtiofsd), which is itself an escape vector when unconfined. The confinement is the sandbox, the syscall filter, unprivileged execution, a read-only host source where applicable, and one daemon per share — a share's cache mode is coherency policy and is not part of this invariant ([`../../decisions/ADR-0039-share-cache-policy.md`](../../decisions/ADR-0039-share-cache-policy.md)). See [`../../decisions/ADR-0024-backend-security-requirements.md`](../../decisions/ADR-0024-backend-security-requirements.md) and the enactment in [`../../decisions/ADR-0027-vmm-and-virtiofsd-hardening-launch-profile.md`](../../decisions/ADR-0027-vmm-and-virtiofsd-hardening-launch-profile.md).

## Build and determinism

- N3 — Pure build. The sandbox build MUST NOT take any host-specific value as input beyond what the manifest itself declares. Given the same manifest closure and lockfile, it MUST evaluate to the same store output on any machine and at any later time. A declared workspace is the one place a manifest carries a host path that a build output depends on: its expanded `source` is also its guest path, so two machines resolving one manifest to different paths produce different store outputs, and that is the manifest's own text differing rather than the build reading the host ([`../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md`](../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md)). See [`04-composition-and-determinism.md`](./04-composition-and-determinism.md).
- N4 — Output hash is the freshness key. Freshness MUST be derived from the build's store output, not a separately computed content digest. Changing any layer changes the inputs and thus the output.
- N19 — Launch-channel data never enters the build. Runtime declarations — mounts, runtime environment, and resource ceilings, however declared — MUST be read by pure evaluation and applied at launch; no build output may depend on them, and host-side variable expansion MUST happen only at launch. Volume declarations are not launch-channel data: a volume's guest mountpoint is guest system configuration, so the build legitimately depends on it. Neither is a declared workspace: it is mounted at the path the host holds it at, so its expanded `source` is also its guest path and the build legitimately depends on that too ([`../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md`](../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md)). Both remain declarations a user writes; what is decided per option is which channel carries the value. See [`04-composition-and-determinism.md`](./04-composition-and-determinism.md), [`../../decisions/ADR-0021-typed-launch-channel-options-in-pieces.md`](../../decisions/ADR-0021-typed-launch-channel-options-in-pieces.md), and [`../../decisions/ADR-0041-resource-and-volume-channel-classification.md`](../../decisions/ADR-0041-resource-and-volume-channel-classification.md).

## Composition

- N6 — No custom merge engine. Layer composition MUST be performed by the NixOS module system, not a bespoke merge implementation. See [`../../decisions/ADR-0002-module-system-as-composition-engine.md`](../../decisions/ADR-0002-module-system-as-composition-engine.md).
- N7 — The manifest is the sandbox key. A working directory MUST resolve to exactly one manifest through the fixed precedence, resolution MUST fail closed when none or more than one applies, and every per-sandbox state, data, cache, runtime, volume, and unit name MUST use that manifest name with the target component unchanged. See [`../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md`](../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md), which supersedes [`../../decisions/ADR-0011-config-read-only-binding-in-state.md`](../../decisions/ADR-0011-config-read-only-binding-in-state.md).

## Network

- N8 — Egress defaults to open. Egress MUST default to unrestricted, with a single declarative knob to switch to a default-deny allowlist. Open egress MUST NOT be described as weakening the isolation boundary. See [`05-networking-and-egress.md`](./05-networking-and-egress.md).

## Project environment

- N9 — User files are never modified. vivarium MUST NOT modify a project's own user-authored files, including its development-environment configuration; the project's environment MUST work identically in or out of the sandbox. There is no tool-owned exception inside a workspace. See [`06-workspace-and-project-environment.md`](./06-workspace-and-project-environment.md) and [`../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md`](../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md), which supersedes the marker decisions recorded in [`../../decisions/ADR-0029-project-identity-and-marker.md`](../../decisions/ADR-0029-project-identity-and-marker.md) and [`../../decisions/ADR-0043-identity-marker-lifecycle.md`](../../decisions/ADR-0043-identity-marker-lifecycle.md).
- N16 — Host-symmetric workspace set. Every declared workspace MUST be mounted read-write inside the guest at the same absolute path it occupies on the host, so a path either side records resolves on both. Each share's internal mount point MUST be a build-time constant and the guest MUST bind the share at its target from its own table; a declared workspace is the row whose target is its own `source` ([`../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md`](../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md)). A path that equals, contains, or lies under a path the guest owns, and two workspace paths that are equal or nested, MUST be refused when the manifest is resolved, before any evaluation, by every command that resolves one. See [`06-workspace-and-project-environment.md`](./06-workspace-and-project-environment.md), [`../../decisions/ADR-0108-a-workspace-is-owned-by-one-manifest.md`](../../decisions/ADR-0108-a-workspace-is-owned-by-one-manifest.md), and [`../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md`](../../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md), which supersedes [`../../decisions/ADR-0100-the-workspace-mirrors-its-host-path.md`](../../decisions/ADR-0100-the-workspace-mirrors-its-host-path.md) on mechanism.

## Secrets and sharing

- N10 — No secrets in the store. A secret MUST NOT enter the build or the Nix store. Secrets are runtime-injected or encrypted-at-rest only. This reaches the manifest's own text, which is compiled into the generated flake and therefore lands in the store — including its launch-channel tables. N19 keeps a launch-channel value out of every build output; it does not keep the text that declares it out of the store, and a declared workspace's expanded path reaches a build output as well as the store (N19) ([`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md), [`../../decisions/ADR-0058-generated-flake-is-a-materialized-cache-artifact.md`](../../decisions/ADR-0058-generated-flake-is-a-materialized-cache-artifact.md)). See [`../../decisions/ADR-0010-secrets-never-in-nix-store.md`](../../decisions/ADR-0010-secrets-never-in-nix-store.md).
- N11 — Shared config is personal-data-free. A shared artifact — an image or a piece — must not contain literal personal paths or plaintext secrets; such data belongs to the personal class, the user's own manifest chief among it. Unexpanded portable variables — `${HOME}` and the XDG directory names enumerated there — are not personal paths; they are machine-independent names resolved at launch. The two clauses differ in what the tool can do about them, and the difference is part of the invariant rather than a gap in it: a literal path is decidable from artifact text and is refused at evaluation with `65`, while a plaintext secret is not decidable by inspection and is served by a heuristic warning only ([`13-doctor-and-health-checks.md`](./13-doctor-and-health-checks.md)). See [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md) and [`../../decisions/ADR-0040-manifest-is-the-personal-layer.md`](../../decisions/ADR-0040-manifest-is-the-personal-layer.md).
- N17 — Guest environment is deny-by-default. Host environment variables MUST NOT be forwarded wholesale into the guest; only the specified allowlist and explicit per-invocation `--env` values may cross the boundary. A declared agent channel is not an exception: the guest's agent variable is set by the guest agent to a fixed guest path, never copied from the host. See [`12-exec-and-shell.md`](./12-exec-and-shell.md) and [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md).
- N24 — Host session directories never cross. A mount `source` MUST NOT resolve to the host's `/tmp`, `/var/tmp`, or `${XDG_RUNTIME_DIR}`, nor to any ancestor of them, in either the shared or the personal layer. These hold live session state — display and session-bus sockets, authentication-agent sockets, and other processes' temporary files — and a share cannot convey a working socket anyway, so mounting one grants exposure without ever granting the capability that motivated it. Credentials cross through the declared channels of [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md); guest scratch is the per-VM ephemeral layer ([`06-workspace-and-project-environment.md`](./06-workspace-and-project-environment.md)). See [`../../decisions/ADR-0071-agent-forwarding-over-a-second-vsock-port.md`](../../decisions/ADR-0071-agent-forwarding-over-a-second-vsock-port.md).
- N25 — No decryption identity crosses the boundary, and vivarium holds none. vivarium MUST NOT decrypt a secret, execute a decryptor or provider command on the user's behalf, hold or generate a decryption identity, or write decrypted material to any host path. Encrypted-at-rest remains a legal shape for a secret (N10) and is entirely user-owned; what vivarium supplies is the runtime-injection channels, not the cryptography. See [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md) and [`../../decisions/ADR-0072-vivarium-integrates-no-encrypted-at-rest-scheme.md`](../../decisions/ADR-0072-vivarium-integrates-no-encrypted-at-rest-scheme.md).

## State

- N12 — User-based state. All state MUST live under per-user XDG directories, split so that config is authored, data is pinned input, state is runtime, and cache is regenerable. No privileged or shared mutable state. See [`02-config-and-xdg-layout.md`](./02-config-and-xdg-layout.md).

## Lifecycle and history

- N14 — Built generations are GC-pinned. Every build output the tool retains MUST be pinned by a garbage-collector root under the state root, so `viv start --no-rebuild` and `viv start --generation <n>` targets survive `nix-collect-garbage`. See [`11-generations-and-build-history.md`](./11-generations-and-build-history.md) and [`../../decisions/ADR-0014-build-generations-and-gc-roots.md`](../../decisions/ADR-0014-build-generations-and-gc-roots.md).
- N15 — `viv start` is idempotent and non-destructive. A fresh, already-running VM re-starts to a no-op; `viv start` MUST NOT stop or replace a running VM without an explicit `--rebuild`. See [`10-vm-lifecycle.md`](./10-vm-lifecycle.md) and [`../../decisions/ADR-0013-vm-lifecycle-and-up.md`](../../decisions/ADR-0013-vm-lifecycle-and-up.md) (which records the verb under its former name `up`; renamed by [`../../decisions/ADR-0018-lifecycle-verbs-and-teardown-boundary.md`](../../decisions/ADR-0018-lifecycle-verbs-and-teardown-boundary.md)).
- N18 — Stop is non-destructive; volumes are removed only explicitly. `viv stop` MUST NOT remove volumes, generations, or state. A project's persistent volumes MUST survive stop, reboot, and rebuild, and MUST be removed only by explicit request — `viv destroy` without `--keep-volumes`, or `viv volume rm`. See [`06-workspace-and-project-environment.md`](./06-workspace-and-project-environment.md), [`10-vm-lifecycle.md`](./10-vm-lifecycle.md), and [`../../decisions/ADR-0019-volume-model.md`](../../decisions/ADR-0019-volume-model.md).

## Resources and capacity

- N22 — Declared resources are ceilings, not reservations. Every resource figure — declared in the manifest or resolved by the auto-sizing policy — MUST bound what a sandbox may use without committing that amount of host memory or disk to it, and the tool MUST NOT require a user to hand-size a sandbox in order to run one. Guest memory is demand-faulted and returned to the host as it is freed; volume images are sparse with a virtual declared size. See [`17-resources-and-capacity.md`](./17-resources-and-capacity.md), [`../../decisions/ADR-0035-elastic-guest-memory-model.md`](../../decisions/ADR-0035-elastic-guest-memory-model.md), and [`../../decisions/ADR-0037-volume-disk-format-and-reclamation.md`](../../decisions/ADR-0037-volume-disk-format-and-reclamation.md).
- N23 — Capacity is checked before launch and never arbitrated behind the user's back. `viv start` MUST refuse when the host cannot serve a minimum free-memory reserve, and MUST warn rather than refuse when the running fleet's measured use makes the new VM a risk. vivarium MUST NOT reclaim memory from a running guest, throttle one sandbox for another, or run a background process that arbitrates between sandboxes; reclamation from the host is an explicit user action (`viv trim`). A guest reclaiming its own free memory — which is what makes N22's ceiling a ceiling — is not host arbitration and is expected to be continuous. See [`17-resources-and-capacity.md`](./17-resources-and-capacity.md) and [`../../decisions/ADR-0036-host-resource-scoping-and-admission-control.md`](../../decisions/ADR-0036-host-resource-scoping-and-admission-control.md).

## Config

- N13 — Config and workspace trees are read-only to the tool. vivarium MUST NOT write, create, or scaffold anything under the config root or a declared workspace as a side effect of running a command; it only reads those user-owned surfaces. Any value the tool persists is state, data, or cache — never config or workspace content. See [`02-config-and-xdg-layout.md`](./02-config-and-xdg-layout.md), [`../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md`](../../decisions/ADR-0107-the-sandbox-keys-on-the-manifest.md), and N9.
