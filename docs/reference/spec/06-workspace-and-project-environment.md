# 06 — Workspace and project environment

vivarium distinguishes two layers: the sandbox it manages, and the project's own development environment that runs inside it. The separation and its rationale are in [`../../decisions/ADR-0008-two-layer-separation.md`](../../decisions/ADR-0008-two-layer-separation.md).

## The mounted workspace

The tool mounts the user's working directory into the guest at the same absolute path it occupies on the host, so the project is reachable by one path string on both sides ([`../../decisions/ADR-0100-the-workspace-mirrors-its-host-path.md`](../../decisions/ADR-0100-the-workspace-mirrors-its-host-path.md)). Symmetry is the point rather than an aesthetic: git's linked worktrees record two absolute paths — a forward pointer under the main repository's `.git/worktrees/`, and a back-pointer in the worktree's own `.git` file, which `git worktree add` writes from the repository it resolved through the current directory and which no argument overrides. A tree reachable only at a guest-invented path therefore yields worktree metadata that resolves on one side and not the other, and the failure is quiet: `git worktree list` reports it healthy from both sides while `remove` and `move` fail from one.

Mirroring the path may not put that path in a build output (N19). So the share itself mounts at a build-time constant the guest owns, the host path crosses on the kernel command line at launch, and a guest unit binds the share at the mirrored path before the agent accepts a session. Two consequences are contract rather than incident: the tree is reachable at both paths, and a mirrored path that equals, contains, or lies under a path the guest owns — the guest home included — is refused before boot with `78` rather than mounted somewhere adjacent.

The mount is:

- Read-write. The project builds, editors write, and tools generate output in place. (Read-only mounts are reserved for injected identity such as credential directories; see [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md).)
- A shared host directory, exposed through the backend's filesystem sharing, so changes are visible on both sides.
- Injected at launch time, never built into the VM. The host path is supplied when the VM starts, which keeps the build pure and reproducible, per [`../../decisions/ADR-0009-launch-time-workspace-path-injection.md`](../../decisions/ADR-0009-launch-time-workspace-path-injection.md).
- Writable by the default guest user used by `exec`/`shell`, as specified in [`12-exec-and-shell.md`](./12-exec-and-shell.md).

Manifests and pieces may declare additional runtime mounts at other guest paths — extra `/workspaces/<name>` repositories or mirrored host config files — through the mount schema decided in [`../../decisions/ADR-0020-mount-and-config-mirroring-schema.md`](../../decisions/ADR-0020-mount-and-config-mirroring-schema.md) and [`../../decisions/ADR-0021-typed-launch-channel-options-in-pieces.md`](../../decisions/ADR-0021-typed-launch-channel-options-in-pieces.md): a host `source` (host-side `${VAR}` expansion at launch), a guest `target` (`~` expands to the guest home), and an optional `readonly` flag. The manifest declares them as TOML `[[mounts]]` entries; a piece declares them as typed `vivarium.mounts` options ([`03-artifact-model.md`](./03-artifact-model.md)); both compile into one merged list — declarations concatenate across layers, and duplicate targets fail evaluation. These mounts follow the same rule as the primary workspace: sources resolve through the launch channel ([`04-composition-and-determinism.md`](./04-composition-and-determinism.md)), never as build inputs, and shared layers reference the host only through portable variables. Config mirroring specifics and the sharing rule live in [`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md).

### How shares are served and confined

A project may declare multiple writable paths (extra `/workspaces/<name>` repositories) and multiple additional bind mounts, each chosen read-only or read-write through the mount schema's `readonly` flag. Every declared share — the primary workspace and each extra mount — is served by its own unprivileged virtiofsd process, confined under the N20 launch profile ([`08-invariants-and-guarantees.md`](./08-invariants-and-guarantees.md), [`../../decisions/ADR-0027-vmm-and-virtiofsd-hardening-launch-profile.md`](../../decisions/ADR-0027-vmm-and-virtiofsd-hardening-launch-profile.md)): `--sandbox=namespace`, seccomp on, with only that share's host path in its view, so one share can never reach another or the wider host filesystem.

A share carries the host's own filesystem boundaries into the guest: a directory that is a separate filesystem on the host is a separate filesystem in the guest. That keeps per-file identity unique across the share, keeps a whole-filesystem sync covering the whole share rather than only its root, and means boundary-respecting tools — `find -xdev`, `du -x`, repository-root discovery — see the same shape they see on the host. It is worth stating precisely because it is the transport's default: an optimization that collapsed those boundaries to save lookups would silently break all three.

Read-only is enforced on both sides: the host source is exposed read-only and the guest mount is `ro,nodev,nosuid,noexec`, so a read-only mount can carry data but never executables or device nodes, and writes are confined to exactly the declared read-write paths. Guest scratch — `/tmp` and other non-persistent locations — is the per-VM ephemeral layer above, never a host mount.

A share is not a general-purpose local filesystem. Three operations are unavailable on any share, read-write ones included: creating an unnamed temporary file that is later linked into place — the atomic create-then-link pattern some toolchains use for output files — creating device nodes, and POSIX ACLs, which are mutually exclusive with the identity translation below. A toolchain that requires any of them must write to a persistent volume or to guest-local scratch, which is the same rule as "keep regenerable caches off the share" below.

### What a source may be

A mount carries filesystem data: a `source` must resolve to a regular file or a directory. A socket, a FIFO, or a device node is refused before boot, naming the credential channel where a socket belongs ([`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md), [`../../decisions/ADR-0071-agent-forwarding-over-a-second-vsock-port.md`](../../decisions/ADR-0071-agent-forwarding-over-a-second-vsock-port.md)). Two reasons, and the first is sufficient on its own:

- It could not work. A share conveys an inode, not a kernel object. A guest that finds a socket inode over a share has a name whose listener lives in the host kernel and is unreachable from a guest with its own (N1) — so the declaration would produce a broken guest rather than an error.
- The flags would mean nothing. `ro,nodev,nosuid,noexec` constrain how a file may be used; none of them constrains connecting to a socket. A socket would be the one entry in this schema where the guarantees that justify the schema do not apply.

A regular-file source is served through its parent directory: a virtiofs share exports a tree, so the share's daemon serves the parent — which for a file mount is the daemon's whole view — and the guest binds the one named file at the declared target, shadowing the share's internal point behind a root-only tmpfs afterward. The shadowing bounds ordinary guest processes, not guest root, which can remount the share's tag and reach the parent's other entries — read-only when the declaration is `readonly = true`, writable otherwise. This residual is accepted and recorded: a user declaring a file mount SHOULD keep that file in a dedicated subdirectory rather than a populated one such as the host home, and an export-level restriction that serves only the declared file is an open design (`Q-031` in `docs/plan/open-questions.md`).

The type check reads the source through an `O_PATH` descriptor the spawning supervisor holds open until every daemon has opened its own root, rather than checking a path and letting an unrelated process re-open it later. The daemon itself re-opens the path when it enters its sandbox — measured against virtiofsd 1.14.0, whose `--sandbox namespace` re-opens its root inside the new mount namespace where a `/proc/self/fd/N` spelling no longer resolves, and the N20 sandbox outranks a descriptor handoff — so a window remains between the supervisor's check and the daemon's open. It is bounded by the same sandbox: the daemon pivots into whatever the path then names and can reach nothing else.

Separately, no mount may take a host session directory as its source — `/tmp`, `/var/tmp`, or `${XDG_RUNTIME_DIR}`, or any ancestor of them (N24). This binds both layers, including a user's own manifest where literal paths are otherwise legal. Such a directory is a rendezvous point for other processes' sockets and temporary files, and read-only does not contain that: a socket confers authority rather than data, and a name in a shared directory can be replaced between one use and the next. A literal session path is decidable from the declaration and fails at evaluation with `65`; one that only appears after host-side expansion is caught at launch with `78`, the same two-tier shape the portable-path rule already uses ([`07-secrets-and-config-sharing.md`](./07-secrets-and-config-sharing.md)).

### Who owns a shared file

The guest user has a fixed UID and GID, chosen when the image is built and identical on every host. Each per-share daemon is launched with a bidirectional one-to-one translation between that pair and the UID/GID of the host user who ran `viv` ([`../../decisions/ADR-0066-share-uid-gid-translation.md`](../../decisions/ADR-0066-share-uid-gid-translation.md)). So a file the guest writes into the workspace lands owned by the host user, a file the host wrote is writable by the guest user, and neither side sees an identity it cannot act on.

The translation is the daemon's own, applied in software. It needs no capability, no host-administered subordinate-ID ranges, and no setuid helper — which is what lets it compose with the unprivileged namespace sandbox N20 requires, rather than fighting it.

Guest identities outside the map are forbidden rather than passed through. A guest attempt to own a shared file as some other user fails with a permission error; it never silently becomes a file owned by the host user, which would be an invisible privilege the guest did not ask for and the host did not grant. Host identities outside the map — files the share contains that some other host user owns — appear under the conventional overflow identity, visible and inert.

It follows that anything acting on the workspace must run as the mapped guest user, including guest-side system tasks. To any other guest identity — the guest's own administrative user included — every file in the workspace belongs to someone else, and ownership-sensitive tooling refuses to proceed rather than degrading: a repository under the workspace will not open. That refusal is this contract holding, not a fault to route around, and the remedies that suppress it — widening the map, or disabling the ownership check — each trade the guarantee for convenience.

The guest UID is deliberately not the host UID. A guest user's numeric identity is guest system configuration and therefore build-channel ([`03-artifact-model.md`](./03-artifact-model.md)); deriving it from the host would put a launch-time value in a build output, break N19, and make one user's cached guest build useless to the next.

### Cache policy per share

A share's cache mode governs coherency, not confinement — it decides how long the guest may trust its own view of a share, and it is deliberately no part of the N20 profile ([`../../decisions/ADR-0039-share-cache-policy.md`](../../decisions/ADR-0039-share-cache-policy.md)). Each share names the policy its content justifies; none is inherited from whatever default is in reach ([`../../decisions/ADR-0050-share-cache-policy-named-by-mechanism.md`](../../decisions/ADR-0050-share-cache-policy-named-by-mechanism.md)):

| Share                                          | Cache policy                   | Why                                                                                                                                         |
| ---------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| The read-only guest store share (below)        | cache aggressively             | Content-addressed paths are never rewritten in place, so no cached page or attribute can go stale — a proof, not a trade-off                |
| The primary workspace and any read-write mount | bounded-timeout, close-to-open | Names and attributes are trusted for about a second and contents revalidate on open, so a host-side edit becomes visible within that window |
| Read-only mirrored config                      | bounded-timeout, close-to-open | Changes rarely, and the same bounded window is more than sufficient                                                                         |

Three of the four available policies are unusable for a host-writable share, and the reasons are correctness, not speed. The two long-timeout policies hold cached names and attributes for a day, and the daemon has no way to push an invalidation to the guest and no way to propagate a host-side change notification — timeout expiry is the only invalidation there is, so an edit made on the host is not merely late, it is unobservable until the share is remounted. The two cacheless policies force direct I/O on every regular file, which makes the guest kernel refuse shared memory-mapping; that breaks executable loading, embedded databases, and toolchains that map their working files, and the daemon's own opt-out for it is documented as safe only where the daemon has exclusive access to the directory — exactly what a host-edited tree does not give it. The fully cacheless policy additionally turns off the bulk directory read, so every entry in a large tree costs its own round trip, which is the opposite of what this workload — dominated by directory walks and small-file metadata — needs.

The store share's aggressive caching carries a sharper proof than immutability alone: because the daemon never caches a failed lookup, a store path created on the host during a running session is still found on first reference. The only staleness the store share can exhibit is a stale listing of the store root, which nothing depends on for correctness.

The daemon's request concurrency is pinned, not inherited. Each daemon's worker-pool size is set explicitly at launch, to a measured fixed number, and is the same for every share ([`../../decisions/ADR-0096-the-share-worker-pool-takes-the-daemon-default.md`](../../decisions/ADR-0096-the-share-worker-pool-takes-the-daemon-default.md)). It is stated rather than assumed because the defaults in play disagree and because the daemon exposes exactly one request queue per share, so its pool size is the only concurrency lever a share has. The surrounding guest-module ecosystem defaults to one worker per host core, which vivarium would multiply by the number of shares in a sandbox and again by the number of sandboxes running at once — a thread count a workstation should not pay ([`17-resources-and-capacity.md`](./17-resources-and-capacity.md)). The value is whatever vivarium's own concurrent measurement supports, and unlike cache mode it is uniform across shares, because pool size is throughput and carries no coherency requirement that could differ from one share to the next. Like cache mode, it is performance, not confinement ([`../../decisions/ADR-0039-share-cache-policy.md`](../../decisions/ADR-0039-share-cache-policy.md)), and it is no part of the N20 profile.

Keep regenerable caches off the share. (Measured: over a byte-identical tree, metadata-heavy work costs about 4.5–5× through the share against the guest's own volume, and content-heavy work about 2.3–3× — [`../microvm-verification-harness.md`](../microvm-verification-harness.md). The ratio is measured; the claim that cache placement is the larger win is not, and is deliberately not made here.) Language and package-manager caches, dependency trees, and build output directories belong on a persistent volume rather than under the workspace share. The reason is filesystem semantics, not a general "shares are slower": the daemon caches no failed lookup under any policy, so a dependency search — which is overwhelmingly misses — pays a host round trip per miss for as long as the sandbox runs, and no cache setting changes that. A volume is a local block device with a full guest filesystem beneath it, where name caching, negative name caching, memory-mapping, and the create-then-link pattern all work natively and cost nothing. The default volume already places everything under the guest home on that side of the line; where a toolchain insists on writing these directories inside the repository, `[volume].persist` (below) is the mechanism.

## The independent inner environment

A project may define its own development environment — a `flake.nix` with direnv, or an equivalent. That environment is the inner layer: it lives in the repository, is owned by the project, and must work identically whether or not the project runs inside a vivarium sandbox. vivarium never modifies it. The sole thing vivarium writes into the project tree is its own self-ignored `.vivarium/` identity marker (N9, N21), which is inert to this inner layer; see [`15-project-identity.md`](./15-project-identity.md).

Two Nix evaluations therefore exist and must not be conflated:

- The outer evaluation builds the sandbox (the VM) from the manifest, on the host, at build time.
- The inner evaluation builds the project's development environment, inside the guest, when a shell enters the workspace.

They are independent: separate configuration files, separate lockfiles, separate evaluations at different times.

## What the guest must provide

For the inner environment to work, the sandbox base must ship a working Nix toolchain (with flakes enabled) and direnv, so that entering the workspace loads the project's environment automatically. Installing these in the guest is a requirement of the two-layer design, not an optional convenience. `viv shell` enters the workspace as a login-interactive shell so direnv can load the inner environment; details are in [`12-exec-and-shell.md`](./12-exec-and-shell.md).

## Persistent volumes

The guest filesystem is three layers: the immutable image built from the store (rebuilt from the manifest, writes lost), an ephemeral runtime layer whose writes vanish at shutdown, and the persistent volumes — the project's mutable data, which survives `viv stop`, reboots, and rebuilds. The model is decided in [`../../decisions/ADR-0019-volume-model.md`](../../decisions/ADR-0019-volume-model.md).

A volume is continuity, not durability. It exists so a warm restart is cheap — caches stay warm, shell state survives, a rebuild does not cost a re-download. It is not a system of record, and vivarium offers no snapshot, rewind, or backup for one ([`00-goals-and-non-goals.md`](./00-goals-and-non-goals.md)). "Not regenerable" below describes what the tool cannot reconstruct, which is why volumes live under state and are never removed implicitly (N18); it is not a promise that what a guest wrote is safe. Anything unique belongs in the workspace, on the host, under version control.

- The default volume always exists, has the reserved name `default`, and is mounted at the guest user's home — so shell state, tool and language caches, dotfile state, and user-run data under `$HOME` persist without declaration.
- Named volumes are declared in the manifest (`[[volumes]]` with `name`, `mount`, and an optional `size_gib`) or contributed by pieces through the `vivarium.volumes` option (declarations concatenate; the same name with conflicting mountpoints fails evaluation). Each becomes its own disk, mounted at its declared guest path, with its own lifecycle under `viv volume`. Unlike mounts and resource ceilings, a volume declaration is build-channel — the guest mountpoint is guest system configuration, so adding a volume rebuilds, and only the host image path and virtual size resolve at launch ([`../../decisions/ADR-0041-resource-and-volume-channel-classification.md`](../../decisions/ADR-0041-resource-and-volume-channel-classification.md)).
- `[volume].persist` lists extra guest paths (for example a system service's data directory) bind-mounted from inside the default volume, so their writes persist without a separate disk. The same singular table carries `size_gib` for the default volume's own ceiling; it is a separate table from `[[volumes]]` because TOML forbids one name serving as both a table and an array of tables ([`03-artifact-model.md`](./03-artifact-model.md)).
- Physically, each volume is one host-side disk image under the state root (`projects/<project-id>/<target>/volumes/<name>.img`) attached as a block device — state, never cache, because volume contents are user data and not regenerable ([`02-config-and-xdg-layout.md`](./02-config-and-xdg-layout.md)). Identity is (project, target, name): manifests declare the shape, each bound project instantiates its own private volumes, and reattachment on `viv start` is automatic. The `<project-id>` and `<target>` components are defined in [`15-project-identity.md`](./15-project-identity.md).
- Each image is sparse and raw, created lazily on the first `viv start` that needs it, and its declared size is a virtual ceiling: the image occupies what its contents occupy, and space freed inside the guest is returned to the host by periodic and on-demand trim (N22, [`../../decisions/ADR-0037-volume-disk-format-and-reclamation.md`](../../decisions/ADR-0037-volume-disk-format-and-reclamation.md)). A volume's ceiling may be raised between boots; it is never lowered in place. Sizes, defaults, and the allocated-against-virtual reporting are in [`17-resources-and-capacity.md`](./17-resources-and-capacity.md).
- The store volume backs the guest store's writable layer and its database. It is not declared, has no mountpoint a user chooses, and is unlike every volume above in two ways: it must be attached and mounted in the guest's initrd, before `/nix/store` is assembled and therefore before the machinery that mounts the others exists; and its contents are regenerable, so it is the one volume whose loss costs a re-fetch rather than data. It carries a size ceiling like any other and is reclaimed by `viv volume rm` and by `viv destroy` ([`../../decisions/ADR-0087-the-inner-store-persists-on-its-own-volume.md`](../../decisions/ADR-0087-the-inner-store-persists-on-its-own-volume.md)), and it is the one volume provisioned for file count as well as for size, because the store's density would otherwise exhaust a default filesystem's inodes before its blocks ([`17-resources-and-capacity.md`](./17-resources-and-capacity.md)). It is a block device and could not be a share: the overlay above it records a deleted path as a device node, which a share cannot hold — so the writable layer is a disk for a kernel reason independent of the persistence one. It is listed like any other volume, with no declaring layer ([`01-command-surface.md`](./01-command-surface.md)): a volume the user never declared is still one whose space they pay for, and it cannot be removed from a list it is not in ([`../../decisions/ADR-0090-the-guest-store-volume-is-listed.md`](../../decisions/ADR-0090-the-guest-store-volume-is-listed.md)). Because it mounts before the guest has an identity to own it, the first-boot ownership and seeding rules below do not apply to it.
- Anything written outside `$HOME`, a named volume's mountpoint, a `persist` path, or the guest store is ephemeral and lost at shutdown.
- Volumes are removed only on explicit request — `viv destroy` (all of them, unless `--keep-volumes`) or `viv volume rm` (which refuses while the VM runs) — never by `stop` or a rebuild (N18, [`08-invariants-and-guarantees.md`](./08-invariants-and-guarantees.md)).
- An orphan is a volume image still on disk under the project's state that no current layer declares — the residue of a volume dropped from the manifest or from a piece. The two volumes that exist without ever being declared, the default home volume and the store volume, are excluded by construction: they match the predicate's letter while being entirely live, so `orphan` is `false` for both and `prune` never considers them. It keeps occupying space and is never removed implicitly, precisely because a declaration can be removed by accident and the data is not regenerable. `viv volume list` flags orphans so the space is visible before `viv volume rm` reclaims it, and `viv volume prune` reclaims all of them in one step ([`../../decisions/ADR-0067-volume-prune-and-first-boot-home.md`](../../decisions/ADR-0067-volume-prune-and-first-boot-home.md)).
- `prune` removes orphans and nothing else. Its candidate set is exactly the orphan predicate above — the same one `volume list` reports — so it introduces no second notion of "unused" that could drift from the first. A declared volume is never a candidate, under any flag: there is no `--all`, and the command to remove data that is still declared is `viv volume rm` or `viv destroy`, both of which say so in their names. Removing orphans is not the same operation as `trim`, which returns free space from inside volumes that are kept.

Exit codes for `viv volume list` / `rm` / `trim` / `prune` follow the per-command matrix in [`14-exit-codes.md`](./14-exit-codes.md) — notably `75` when `rm` or `prune` refuses because the VM is still running (stop first).

### First boot of a volume

A volume's image is created lazily, so the first `viv start` that needs one attaches an empty filesystem whose root is owned by the guest's system identity, not by the guest user. Left alone, that would make the default volume — mounted at the guest user's home — unwritable by the very user who lives there.

vivarium's guest module ([`../../decisions/ADR-0048-guest-module-only-vivarium-owns-the-runner.md`](../../decisions/ADR-0048-guest-module-only-vivarium-owns-the-runner.md)) therefore declares the required ownership and mode for each volume's mount point, applied after that volume mounts and before the agent accepts a session — so no session ever observes the unowned state. The default volume's home is additionally seeded once from the image's skeleton, guarded by a marker stored inside the volume itself, so a rebuild or a later boot never re-seeds over data the user has since written. The same declaration covers each `persist` path.

Two things this deliberately does not do. It does not repair ownership recursively: the work would be proportional to a home that legitimately grows to tens of gibibytes, on every boot, and it would overwrite ownership the user set on purpose. And it does not treat a later boot as a first boot: after the marker exists, vivarium verifies the mount point and touches nothing below it.

## The store inside the guest

The guest reads the host's Nix store, shared read-only, decided in [`../../decisions/ADR-0038-guest-store-sharing.md`](../../decisions/ADR-0038-guest-store-sharing.md). This is contract, not an implementation detail, because it is what makes each additional running project nearly free: no per-VM store image is built, no store bytes are duplicated, and one host page cache serves every guest's store reads. The saving is on the host side of the share. Guests do not share the pages they have read — see the note on deduplication in [`17-resources-and-capacity.md`](./17-resources-and-capacity.md).

- The store share is read-only on both sides and served by its own confined daemon, exactly like every other share, with the aggressive cache policy justified above.
- A writable overlay sits above it inside the guest, so `nix build` and the project's own inner environment work normally ([`04-composition-and-determinism.md`](./04-composition-and-determinism.md)); writes land in the overlay, never in the host store.
- The trade is stated rather than hidden: a guest can enumerate every path in the host store. The store is world-readable by construction and never holds secrets (N10, [`../../decisions/ADR-0010-secrets-never-in-nix-store.md`](../../decisions/ADR-0010-secrets-never-in-nix-store.md)), and the boundary protects against escape, not against a guest learning which packages the host has built.
- The store's guest mount is deliberately excluded from the ordinary shutdown ordering. Everything the guest needs in order to shut down, the unmount tooling itself included, lives in that store, so letting the shutdown transaction try to release it first is a deadlock. `viv stop` therefore completes within its timeout regardless of how the store is provided ([`10-vm-lifecycle.md`](./10-vm-lifecycle.md)).
- Physical presence is not validity, and the inner layer does not rely on it. Only the guest system's own closure is registered in the guest's store database; every other host store path is readable through the share and formally unknown to the guest's Nix. This is the contract rather than a limit awaiting repair. The share exists to deliver the guest's own closure, which is the whole of the saving this section claims, and the project's inner environment provisions itself: whatever it fetches or builds lands in the writable overlay above, and vivarium never bridges host store bytes into it ([`../../decisions/ADR-0084-the-inner-layer-provisions-its-own-store.md`](../../decisions/ADR-0084-the-inner-layer-provisions-its-own-store.md)). vivarium therefore assumes nothing about the host beyond the Nix it builds with — a sandbox behaves identically whether the host's store holds twenty thousand paths or two hundred. Verified in [`../microvm-verification-harness.md`](../microvm-verification-harness.md).
- What that costs the inner layer, stated. An inner `nix build` or `nix develop` treats a host path it can see as missing and obtains it the ordinary way. Under the default open egress that succeeds ([`05-networking-and-egress.md`](./05-networking-and-egress.md)); under `allowlist` mode the substituter must be named in `egress.allow`, or the tool declared in the image instead. The cost is therefore a fetch, not a failure — and it is paid once, not once per boot, because what it obtains lands in the store volume below.
- Sharing is by store path, so it turns on the pin rather than the version. A package the image declares is in the guest's registered closure and is used in place, with nothing fetched and nothing duplicated. The same package named by a project's own `flake.nix` is the same store path only if it resolves to the same inputs; a different `nixpkgs` pin is a different hash, and Nix materializes it separately — which is correct behaviour, not a defect. A project that pins its inner environment to the same `nixpkgs` the image uses therefore gets the share for free, and that is the one lever a user has over a guest's store footprint.
- The writable layer persists on its own volume, and so does the store database. The layer the guest writes to is backed by a disk rather than the ephemeral runtime layer, so a package installed inside the sandbox is still there after `viv stop` and after a host reboot ([`../../decisions/ADR-0087-the-inner-store-persists-on-its-own-volume.md`](../../decisions/ADR-0087-the-inner-store-persists-on-its-own-volume.md)). The database persists beside it because physical presence is not validity — paths without their registration would be present and formally unknown, which is the condition above, self-inflicted. This is continuity, not durability: every path in it is regenerable from a substituter, so losing the volume costs a re-fetch and nothing else ([`../../decisions/ADR-0080-the-sandbox-is-disposable.md`](../../decisions/ADR-0080-the-sandbox-is-disposable.md)).
- The guest's store is a `local-overlay` store, and this is what makes collection inside a guest safe. Nix's collector enumerates the store directory and deletes what its database does not know, so on a plain overlay a guest-side collection deletes host paths it never registered — which cannot touch the read-only host store and instead writes whiteouts into the writable layer, permanently hiding those paths from that guest. The `local-overlay` store type leaves a path that exists only in the lower layer alone, and deletes a duplicated one through the upper layer rather than through the merged view ([`../../decisions/ADR-0088-the-guest-store-is-a-local-overlay-store.md`](../../decisions/ADR-0088-the-guest-store-is-a-local-overlay-store.md)). Its lower store is described by the boot-time registration that ships in the build closure — never by anything read from the host at runtime, which is what keeps the rule above intact. That same database is what decides whether a path is shared or copied: the check is validity in the lower store, not physical presence, so a host path outside the boot closure is materialized in full even though its bytes are already below. This is the mechanism behind the cost stated two bullets up, and it applies to writing as much as to collecting — Nix replaces a store path by deleting the destination first, so an unregistered path below is unlinked and copied rather than reused ([`../microvm-verification-harness.md`](../microvm-verification-harness.md)). The same database decides how a deletion behaves, and the consequence is stated here rather than discovered: a duplicate of a path the lower store knows is deleted through the upper layer and the merged view falls back to the lower copy, but a path the guest materialized whose registration the lower store lacks is deleted through the merged view and leaves that path hidden from this guest thereafter. Nothing the guest never materialized is ever hidden, which is the guarantee that matters; what a guest loses is the sharing of paths it had already chosen to copy.
- The guest's link farm is its own. Nix derives its store-optimization directory from the store's own root, which over an overlay resolves into the shared host store — so a guest collection would otherwise traverse the host's entire link farm over the share, and write into its own layer while doing so. That path is masked inside the guest, which costs nothing because store optimization cannot work across overlay layers and is disabled here regardless ([`../../decisions/ADR-0092-the-guest-masks-the-host-link-farm.md`](../../decisions/ADR-0092-the-guest-masks-the-host-link-farm.md)). A guest collection therefore costs what the guest's own store costs, not what the host's does.
- The guest collects on space pressure, and on nothing else. The guest's Nix daemon collects when free space on the store volume falls below a floor and stops at a target, both stated in [`17-resources-and-capacity.md`](./17-resources-and-capacity.md). Over an overlay a free-space reading reports the writable layer's own filesystem, so the trigger measures the store volume and nothing else. There is no boot sweep and no timer: a sweep at boot deletes the warm cache the volume exists to hold and charges the user for it while they wait, and wall-clock is uncorrelated with pressure ([`../../decisions/ADR-0089-the-guest-store-is-collected-on-space-pressure.md`](../../decisions/ADR-0089-the-guest-store-is-collected-on-space-pressure.md)). The store type above is what makes such a collection safe; the two thresholds are what arrange for one, and they are declared in the guest's own Nix rather than only specified here. The trigger is measured on a running daemon: it fires strictly below the floor rather than at it, and frees exactly the target minus what is available ([`../microvm-verification-harness.md`](../microvm-verification-harness.md)).
- The host store must not change while a guest is running. It is an overlay lower layer inside the guest, and changing a lower layer under a mounted overlay is undefined behaviour, so a host garbage collection under a running guest is outside this contract. The obligation belongs to the decision that shares the live store ([`../../decisions/ADR-0038-guest-store-sharing.md`](../../decisions/ADR-0038-guest-store-sharing.md)).
- A running guest's closure stays pinned, and no new root is taken to do it. A VM boots from a generation, and every generation symlink is already a garbage-collection root under the state root (N14, [`11-generations-and-build-history.md`](./11-generations-and-build-history.md)), so what the guest reads is out of a collection's reach for as long as that generation is retained. The obligation this creates is therefore a refusal, not a registration: `viv generations prune` will not unlink the generation a running VM was booted from, and `viv destroy` stops the VM before it unlinks anything ([`10-vm-lifecycle.md`](./10-vm-lifecycle.md), [`../../decisions/ADR-0085-a-running-guest-pins-the-store-paths-it-reads.md`](../../decisions/ADR-0085-a-running-guest-pins-the-store-paths-it-reads.md)). Nothing is written at `viv start` and nothing is released at `viv stop`, so no stale pin can outlive a crash.
- The pin is not the whole guarantee, and the rule above is still the contract. A root prevents collection of the closure; it does not prevent a direct deletion, nor collection of a path outside it. `viv doctor` therefore reports `store-roots-intact` when a running guest's closure is no longer whole on the host ([`13-doctor-and-health-checks.md`](./13-doctor-and-health-checks.md)) — the failure is named rather than left to surface as an unexplained fault inside the guest. Neither half is implemented yet. A persistent store volume raises what breaking the rule costs, from one session to a project whose store is stranded, which is why that check's invoked-only trigger is provisional ([`../../decisions/ADR-0085-a-running-guest-pins-the-store-paths-it-reads.md`](../../decisions/ADR-0085-a-running-guest-pins-the-store-paths-it-reads.md)).
- An independent per-VM store is refused, in every profile. It would hold one copy of the base per sandbox where the shared store holds one in total — inverting the scaling property [`00-goals-and-non-goals.md`](./00-goals-and-non-goals.md) states as contract, and making vivarium cost more disk than the container model it is measured against rather than less ([`../../decisions/ADR-0086-per-vm-store-duplication-is-refused.md`](../../decisions/ADR-0086-per-vm-store-duplication-is-refused.md)). No flag selects it, and no future hardening may reach for it.
- A store shared writable between guests is not admissible either. The shared read-only host store above is therefore the one admissible shape, with the two alternatives refused for unrelated reasons: duplication on scaling grounds, and a writable share because a database serving several guests would span separate kernels and because one guest could then write a path another executes. The reasoning is recorded in [`../../decisions/ADR-0038-guest-store-sharing.md`](../../decisions/ADR-0038-guest-store-sharing.md).
