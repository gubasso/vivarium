This is triage, not a queue. Every question blocks named work and leaves through exactly one recorded exit.

## Q-007 — Is the pinned Nix derivation JSON stable enough for the purity lane?

Blocks: slice 007 purity acceptance. Raised: ADR-0077's experimental-interface caveat. Exit: a slice 007 `Revisions` line after revalidation, either retaining the interface or naming the replacement.

## Q-009 — Does the generated flake carry a baseline pin for its own inputs?

Its `nixpkgs` and `microvm` inputs name branches, so the first evaluation of every target resolves them from upstream `HEAD`, and two projects bound a day apart silently get different revisions — an input jump nobody announced (N3). The development half of this is settled and is no longer what the question asks: every lane pins the baseline to the store paths this repository's own [`nix/flake.lock`](../../nix/flake.lock) resolves to, through the seam [`BaselineInputs`](../../src/config/flake.rs) reads, so the suite makes no upstream request at all. What stays open is the shipped default: whether a released vivarium should also carry a pin, which would remove the drift and create an obligation to move that pin. Blocks: nothing in flight. Raised: landing item 5, where branch resolution exhausted the anonymous GitHub rate limit and closed the `ConfigEval` gate. Exit: either a rendered baseline pin with a named update path, or a recorded decision that a released tool resolves live and the drift is the user's to pin through their lock.

## Q-010 — How does the supervisor publish the descriptor limit the contract asserts?

The limit is spelled six times across a boundary Nix cannot cross: `524_288` in [`spec.rs`](../../src/launch/spec.rs), and `524288` in [`policy.rs`](../../src/launch/policy.rs), [`systemd.rs`](../../src/launch/systemd.rs), [`launch-arguments.nix`](../../nix/launch-arguments.nix), [`contract.sh`](../../tests/nix/contract.sh), and [`base-image-check`](../../tests/host/base-image-check). Nothing derives one from another, so the contract's assertion is a literal restated rather than two independently realised artifacts compared — the defect that file's own header exists to avoid. Blocks: eliminating the last literal-only cross-boundary assertion. Raised: ADR-0098's deferred gap. Exit: a supervisor introspection subcommand that emits its constants, which the contract then diffs against the launcher JSON.

## Q-013 — Can `config sources` report an irreconcilable merge?

[`01-command-surface.md`](../reference/spec/01-command-surface.md) fixes `conflicts` at four kinds — `tie`, `literal-path`, and slice 019's `session-path` and `non-portable-variable` — so a duplicate volume name — spec/14's own cited instance of an irreconcilable merge — has nowhere machine-readable to go, and slice 019's duplicate mount target joined it on the same irreconcilable channel. `viv config eval` refuses it with `65` as specified, and the provenance view a user reaches for next reports nothing about it. Widening the vocabulary is the obvious fix and is exactly the kind of change the two-field entry was kept narrow to avoid. Blocks: nothing in flight; it is a gap in the pair's division of labour rather than a defect in either half. Raised: reviewing item 5. Exit: either a third `kind` with the trial that reads it, or a spec line saying an irreconcilable merge is `config eval`'s to report alone.

## Q-017 — Should the guest home move out of `/home`?

The guest user's home is `/home/vivarium` ([`../../nix/guest.nix`](../../nix/guest.nix)) and it is an ext4 volume, so it is the one guest-owned path that a mirrored host path can plausibly collide with: a host user named `vivarium` keeps their projects under exactly `/home/vivarium`. ADR-0100 refuses that case rather than mounting into a user's persistent home, which is correct and is also a limitation with no workaround the user can apply. Moving the guest home to a path no host user can occupy would remove the collision entirely, but the home path is build-channel and spec-visible — [`../reference/spec/06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) says the default volume mounts at the guest user's home — so it is a decision rather than a rename. Blocks: nothing; the refusal is safe and named. Raised: enumerating ADR-0100's refusal set. Exit: either a decision moving the guest home with the volume mount point and first-boot seeding following it, or a recorded decision that the refusal is the permanent answer.

## Q-018 — How does `viv stop --timeout` reach the supervisor that owns the graceful rung?

[`10-vm-lifecycle.md`](../reference/spec/10-vm-lifecycle.md) gives the operator a grace period and says `-1` waits indefinitely, and the flag is fully honoured on the host side: [`grace_seconds`](../../src/cli/lifecycle.rs) turns it into the deadline `stop_unit` polls to before it reaches for `systemctl kill`. The rung it is meant to bound is somewhere else. Powering the guest down is the supervisor's, and the supervisor was started by `viv start` — it raises the ACPI power button, waits [`GUEST_POWEROFF_TIMEOUT`](../../src/launch/supervisor.rs), and destroys the VM, with nothing carrying the stop-time value across to it. So `--timeout 30` and `--timeout -1` both buy a longer wait before the group is killed and the same six seconds before the guest is destroyed, which is the opposite of what the flag is for: the point of asking for longer is to let a slow guest finish committing. Widening the constant is not available as a repair, because the ladder has to fit inside the ten-second default when no flag is given. Blocks: [slice 027](./slices/027-the-stop-ladder-is-whole/README.md) item 2, which is where the ladder gains the rung this flag was written to bound; slice 014 item 3 already fixed the durability defect the default grace was losing writes to, and the flag's reach is the separate half that remains. Raised: the first review round of slice 014. Exit: either a launch-time channel that carries the requested grace to the running supervisor before its cancellation path runs, or a recorded decision that the graceful rung is bounded by the shipped default and `--timeout` bounds only the hard one, with `10-vm-lifecycle.md` amended to say so.

## Q-020 — What raises a volume's ceiling once its image exists?

[`06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) says a volume's ceiling may be raised between boots and never lowered in place, which reads as a promise a user can act on by editing `size_gib` and restarting. Nothing performs the raise. [`provision_volumes`](../../src/launch/supervisor.rs) creates an image only when none is there, so a larger declaration reaches the launch contract and the guest keeps the filesystem its first boot was given; `viv volume list` then reports the image's own length, which is the ceiling actually in force rather than the declared one, so the two views do not contradict each other and nothing is reported as wrong. Growing it is not a line: the file has to grow and then the filesystem inside it, which needs `resize2fs` in the backend program set and a decision about whether the check it wants runs first. Blocks: nothing in flight; a user who outgrows a volume today recreates it by removing the image. Raised: a review round of slice 014 items 4 to 6. Exit: either an offline grow step before attach, with the program set and the failure code it answers on, or a spec amendment saying a ceiling binds at creation and a raise takes effect only for an image that does not exist yet.

## Q-021 — What is the `--json` record for `viv stop` and `viv destroy`?

[`10-vm-lifecycle.md`](../reference/spec/10-vm-lifecycle.md) binds both verbs in one sentence — empty stdout on success, one record under `--json` — and no page fixes that record's shape, unlike every data command whose fields [`01-command-surface.md`](../reference/spec/01-command-surface.md) enumerates. Neither verb emits one, so `viv stop --json` and `viv destroy --json` succeed with zero bytes on stdout and a caller that selected machine mode gets nothing to parse. Inventing a shape from inside either verb would settle a two-command contract from one side, and the two have different things to say: a stop reports which rung of the ladder ended it, while a destroy reports what it removed and what it spared, which is already a value the prompt renders. Blocks: [slice 027](./slices/027-the-stop-ladder-is-whole/README.md) item 4, where `viv stop --all` makes the record unavoidable because a sweep's result is per sandbox rather than one state change; until then both verbs are scriptable on their exit code. Raised: a review round of slice 014 items 4 to 6. Exit: either one `01-command-surface.md` entry fixing both records' fields, with the verbs rendering them, or a spec amendment withdrawing the `--json` record for side-effect verbs and leaving the exit code as the machine-readable result.

## Q-024 — What stops a sandbox whose trial process never ran its own cleanup?

[`TempProject`](../../tests/support/mod.rs) already answers the ordinary case, and its own comment records the measurement that forced it: a detached start outlives the process that submitted it, `systemd-run --collect` reaps only an inactive unit, so a trial that starts a VM and never stops one leaves it running. The repair is `stop_leaked_vms` in `Drop`, selecting units by the runtime directory in their own command line so a developer's own sandbox is never matched. What `Drop` cannot cover is the process not finishing: a trial killed by a harness timeout or a signal never runs it, and nothing else sweeps, because cleanup lives in the test process and no runbook under [`../../tests/host/`](../../tests/host/) looks for a stranded unit. Observed on 2026-08-13: three `vivarium-shell-project-t*` units from the 2026-08-12 run were still active twenty-seven hours later, each holding a live `cloud-hypervisor` process and roughly 0.4 GiB, all three from `workflow_06_shell` — the one trial driving a real terminal, and so the one most likely to be killed rather than to return. Blocks: nothing in flight; the units are stopped by hand once seen, and distinct project ids mean the next run does not collide. Raised: inspecting the host while hand-running slice 014's `Done when`. Exit: either a sweep the host runbooks call before and after a capable-host run, keyed on the same command-line match `Drop` uses, or a recorded decision that an interrupted run is the operator's to clean up, said where the operator reads it.

## Q-025 — Should the pair's input hook be default-deny rather than unfiltered?

The allowlist's enforcement lives entirely on the forward hook: [`base_ruleset`](../../src/net/nft.rs) filters what the guest sends through the tap toward the uplink, while traffic delivered locally to the namespace's own addresses takes the input hook, which the table leaves unfiltered. The safety argument is that the gating resolver is the namespace's only listener, so the open input path admits exactly guest-to-resolver DNS — but that is a property of what the supervisor happens to spawn, not a rule the kernel enforces. Any later process joined into the pair with a listening socket — a widened uplink, a debugging tool left behind, a fixture that outlives its trial — becomes guest-reachable with no rule changing and nothing failing, which is how an enforcement gap arrives silently. Blocks: nothing in flight; today's process set makes the property true, and the trials that would notice a second listener ([`tests/user_workflows.rs`](../../tests/user_workflows.rs) probes the resolver socket from inside the pair) observe the process set, not the policy. Raised: reviewing slice 004's merged pass, where removing the forward chain's inert DNS-accept rule surfaced that guest DNS reaches the resolver over the input path. Exit: either an input chain in `base_ruleset` admitting established flows and guest-to-resolver DNS with the same reject-not-drop tail the forward chain carries, or a recorded decision that the single-listener property is the guarantee, with the comment on `base_ruleset` naming it load-bearing.

## Q-026 — What distribution should size the agent-startup budget?

[`AGENT_STARTUP_TIMEOUT`](../../src/launch/supervisor.rs) bounds the rung a `viv start`'s wall clock is dominated by — guest boot to the agent answering on the control socket — and its 20s value is interim: sized as roughly 2.3x one host's ~8.5s end-to-end boot figure, after the previous 10s (a ~1.2x margin) expired twice in one day under host load. Two failures and one end-to-end figure are evidence of possibility, not a distribution, and the constant's comment says so. The launcher-side repair already landed — a failed launch reports through the readiness socket before teardown, so the operator no longer waits out the launcher's 30s to learn nothing — which makes this a calibration question rather than a defect. Blocks: nothing in flight; a budget miss now fails fast with the rung named in the journal. Raised: diagnosing the first-boot workflow, now named `workflow_01_manifest_workspace_resolution_boot`, failing pre-push twice on 2026-08-14, where the supervisor's journal named `timed out waiting for guest agent` while the CLI reported the launcher's 30s. Exit: either a per-rung measurement — `vm.boot` issued to `wait_for_agent` returning, ten boots idle and ten under load resembling the observed pressure — fixing the constant from the distribution with the derivation beside it, or a recorded decision that the agent rung takes the launcher's budget minus reporting headroom and tracks it structurally.

## Q-028 — Where does the created-pin report survive `-q`?

[`16-logging-and-diagnostics.md`](../reference/spec/16-logging-and-diagnostics.md) makes `-q` errors-only on the stderr face, and [`04-composition-and-determinism.md`](../reference/spec/04-composition-and-determinism.md) requires the pin a first evaluation creates be reported — two rules that collide the moment `-q` exists, because the created-pin note travels on stderr and nothing else durable carries it yet. Slice 016 follows spec/16 and suppresses the note under `-q`, so a quiet first evaluation writes a lock nothing announced. The durable substitute spec/16 already names — the always-on diagnostic log file — is slice 005's and is not built. Blocks: nothing in flight; the note still prints in every run that does not pass `-q`, and the lock's existence is inspectable with `viv config`. Raised: shaping slice 016's suppression table, where the conflict fell out of writing the rule down. Exit: slice 005's log file carrying the created-pin record at its default level, or a recorded decision that `-q` waives the spec/04 report and the lock file's own mtime is the trace.

## Q-031 — Is application-agnosticism an invariant, or an unstated habit?

Nothing vivarium ships knows the name of an application. A credential crosses because the user wrote a `[[mounts]]` entry, not because the tool recognized the tool that wants it, and a guest holds exactly the paths the manifest names — no built-in mapping from a program to a host path it is presumed to need. That is a position, and several invariants are consistent with it: N13 refuses side-effect writes to user-owned surfaces, N9 refuses to touch a project's own files, and N11 keeps a shared artifact free of personal paths. None of them states the position itself, so a later change adding a convenience table — well-known credential directories mounted for a recognized program, an agent-specific default, a first-run seeding step — would violate no rule and would be argued case by case. The counterweight is real rather than hypothetical: an alternative in the same class scopes credentials per agent from exactly such a table and gets a finer blast radius than vivarium can express, at the cost of knowing only the seven programs it was written for. Blocks: nothing in flight; a user reading the manifest can already see every path that crosses, which is the property the position exists to give them. Raised: 2026-08-19, comparing vivarium's credential handling against an agent sandbox that scopes credentials from a built-in per-agent table. Exit: either an invariant stating that no host path crosses except by user declaration and that vivarium holds no application knowledge, with the ADR behind it, or a recorded decision that application-agnosticism is a default the product may trade away per feature, which makes the comparison's refusal an ordinary gap instead.

## Q-032 — When the host's default route is a tunnel, does the guest inherit it?

Today it does, silently. The uplink is one unprivileged `pasta` per VM ([`spec/05`](../reference/spec/05-networking-and-egress.md)) that keeps its sockets on the host side and only opens its device inside the pair ([`src/launch/policy.rs`](../../src/launch/policy.rs)), so guest flows are re-originated as host sockets and follow the host routing table. No interface is selected, and the uplink's DNS forward reaches the host's configured resolver, which the gating resolver also forwards permitted names to. A VPN raised by the host's network manager therefore carries the sandbox's traffic and its name lookups, and every private route the tunnel serves becomes reachable from inside a boundary whose whole purpose is that what runs there is not fully trusted. This is the one part of the network the guest does not get its own copy of: namespace, tap, uplink, and resolver are all per-VM, and route selection is inherited. N8 does not cover it — egress mode decides which destinations may be reached, not which host path the packets take — so nothing in the specification names the case either way. `allowlist` mode narrows it without closing it: a permitted destination is still reached over whatever the host route is. The counterweight is an alternative in the same class that binds its uplink to a non-tunnel interface and refuses to run when it cannot find one, treating the tunnel case as fatal rather than degrading. Blocks: nothing in flight; the guest has working egress in both modes. Raised: 2026-08-19, comparing vivarium's uplink against an agent sandbox that selects a host egress interface. Exit: either a declarative knob under `sandbox.egress` naming the posture, with the specification stating what the default is when the host route is a tunnel — inherit, refuse, or carry only the routes the tunnel does not claim — or a recorded decision that host route selection is the operator's, which makes inheritance the stated behavior rather than an unexamined one.

## Q-033 — Does anything outside a sandbox reach a service running inside it?

Today nothing does, and no rule says whether that is the design or an omission. [`spec/05`](../reference/spec/05-networking-and-egress.md) describes egress and says nothing about the other direction; [`spec/00`](../reference/spec/00-goals-and-non-goals.md) does not list inbound reachability as a non-goal. The guest's network lives in its own namespace behind an uplink the launcher starts with no port-forwarding argument, and `exec` and `shell` reach the guest over the vsock control plane rather than a listening socket, so there is no host-visible address and no key to reach one with. The mechanism is not far away — the uplink accepts a forwarding argument and the control plane already crosses the boundary — which is what makes the silence worth resolving rather than assuming. Three ordinary workflows have no answer while it stands: an editor attaching over SSH, a guest development server opened in the host's browser, and a notebook served from inside. Each also carries the reason to be careful, since a forwarded port is a hole in the boundary in the direction the boundary exists to hold, and `viv status` reports nothing that would tell a user one is open. Blocks: nothing in flight; the workflows the tool ships — `exec`, `shell`, and a workspace mounted at its host path — need no inbound path. Raised: 2026-08-19, comparing vivarium's network surface against sandboxes that publish a port. Exit: a declarative knob that names the ports crossing and what reports them, with [`spec/05`](../reference/spec/05-networking-and-egress.md) stating the boundary cost. The refusing branch — a recorded non-goal in [`spec/00`](../reference/spec/00-goals-and-non-goals.md) that a sandbox is reached only through the control plane — is closed: [slice 023](./slices/023-a-declared-port-crosses-inward/README.md) is shaped to build the capability, and what it leaves undecided is only how a declared port is carried. The question stays open until that slice closes, because the work answers it rather than the plan to do the work.

## Q-034 — What tells a user that a shared layer's `vivarium.workspaces` did nothing?

[`ADR-0110`](../decisions/ADR-0110-the-workspace-is-an-ordinary-mount.md) deleted the `vivarium.workspaces` option, so a workspace is no longer something a layer can write: `viv` compiles each `[[workspaces]]` row into a `vivarium.mounts` row from manifest text. Ownership is structural now rather than enforced, which is the improvement. What went with the option is the refusal that could name the offender — [`../../src/config/merged.rs`](../../src/config/merged.rs) used to refuse a layer-declared workspace at `65` naming the layer and its kind, and there is nothing left for it to read.

A piece written against the old spelling is therefore inert rather than refused. [`../reference/spec/04-composition-and-determinism.md`](../reference/spec/04-composition-and-determinism.md)'s provenance view evaluates each layer with `_module.check = false` — deliberately, so an ordinary NixOS layer declaring `services.*` is not fatal there ([`../../nix/vivarium-report.nix`](../../nix/vivarium-report.nix)) — and an undeclared `vivarium.*` is ignored along with it. `viv config eval` succeeds, shows the manifest's own trees, and says nothing about the row the piece wrote. Blocks: nothing; the compiled result is correct and a user who reads the output sees which trees the sandbox owns. Raised: 2026-08-24, enacting `ADR-0110`, where `workflow_03_team_shared_and_personal_override` had asserted the deleted refusal. Exit: either a check that reads each layer's own module text for `vivarium.` attributes the option surface does not declare and reports them as a defect, which would cover every retired option rather than this one; or a recorded decision that a shared layer writing an option vivarium does not declare is the module system's business and vivarium adds no reading of its own, said in [`../reference/spec/04-composition-and-determinism.md`](../reference/spec/04-composition-and-determinism.md) where the provenance view's leniency is specified.

## Q-035 — What runs once, inside the guest, for a project?

vivarium has no surface for a step that runs once when a project's sandbox is first usable. The container-shaped equivalent is an ordinary part of a sandbox definition: the Development Containers specification gives every definition a lifecycle-script family — `onCreateCommand`, `postCreateCommand`, and their siblings, documented at <https://containers.dev/implementors/json_reference/> — for exactly the steps a project needs run once against a fresh environment, such as allowing its direnv or installing its git hooks. The vivarium answer today is a NixOS unit in an image or a piece, which is a build-channel answer to a project-scoped question. A unit in a shared image cannot know which project it will boot for, and a piece that names one project's path is the personal path N11 keeps out of a shared artifact, so the surface that exists is available exactly where it does not fit. A hook point does exist: [`../../nix/guest.nix`](../../nix/guest.nix) already performs first-boot home ownership before the agent starts, ordered by `RequiresMountsFor` against the home volume, so the question is what a user may declare there and not whether anything can run. The counterweight is [`ADR-0084`](../decisions/ADR-0084-the-inner-layer-provisions-its-own-store.md), which already rules that the inner project environment provisions itself — a rule the refusing branch of this question would simply extend. Blocks: nothing in flight; a user runs the step by hand in one `viv shell`, and what it writes persists in the home volume or in the workspace on the host, so it is a first-session cost rather than a per-boot one. Raised: 2026-08-25, pricing what a move from a devcontainer-based workflow to vivarium would cost, where the lifecycle-script family above is the one capability with no vivarium spelling at any layer. Exit: either a declared per-project first-boot step, naming what it may see, what a failure does to the boot, and how it stays out of a shared artifact; or a recorded decision that vivarium runs nothing on the user's behalf inside the guest, said in [`../reference/spec/06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) where the inner layer's independence is specified.

## Q-036 — Does a cache volume belong to a sandbox or to the user?

A volume's image lives under the state root at `projects/<sandbox-id>/<target>/volumes/` ([`../../src/config/volumes.rs`](../../src/config/volumes.rs)), so two manifests declaring the same volume name get two images. For a per-project build cache that is the right scope. For a user-global one — a language runtime's downloaded toolchains, a package manager's cache, a hook-environment store — it duplicates gigabytes per sandbox and warms each copy separately. The container-shaped equivalent has a second scope available: a named volume is an engine-level object with its own lifetime, so one of them mounted by name into several containers is the ordinary way that class of cache is kept warm once rather than per project. Most of the cost is already gone for a reason unrelated to this question: the host store is shared read-only into every guest ([`ADR-0038`](../decisions/ADR-0038-guest-store-sharing.md)), so the largest cache is shared by construction and the whole per-container store-seeding problem does not exist here. What remains is the non-store residue, and the reason it cannot be a rename is concurrency rather than naming: these volumes are ext4 images, two running guests mounting one image read-write is corruption, and the product already refuses a volume in use by a running VM at `75`. Blocks: nothing in flight; a user who wants one warm copy declares the volume in one manifest and reaches the trees from there, which the many-workspaces model makes ordinary. Raised: 2026-08-25, pricing the same move as `Q-035`, where a per-user cache scope is the second capability with no vivarium spelling. Exit: either a declared scope on a volume, with the concurrency rule that scope implies — refusal of a second attach, or read-only sharing after the first — or a recorded decision that a volume belongs to its sandbox and a user-global cache is the inner layer's business, said in [`../reference/spec/06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) beside the volume contract.
