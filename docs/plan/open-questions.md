# Open questions

This is triage, not a queue. Every question blocks named work and leaves through exactly one recorded exit.

## Q-007 — Is the pinned Nix derivation JSON stable enough for the purity lane?

Blocks: slice 007 purity acceptance. Raised: ADR-0077's experimental-interface caveat. Exit: a slice 007 `Revisions` line after revalidation, either retaining the interface or naming the replacement.

## Q-009 — Does the generated flake carry a baseline pin for its own inputs?

Its `nixpkgs` and `microvm` inputs name branches, so the first evaluation of every target resolves them from upstream `HEAD`, and two projects bound a day apart silently get different revisions — an input jump nobody announced (N3). The development half of this is settled and is no longer what the question asks: every lane pins the baseline to the store paths this repository's own [`nix/flake.lock`](../../nix/flake.lock) resolves to, through the seam [`BaselineInputs`](../../src/config/flake.rs) reads, so the suite makes no upstream request at all. What stays open is the shipped default: whether a released vivarium should also carry a pin, which would remove the drift and create an obligation to move that pin. Blocks: nothing in flight. Raised: landing item 5, where branch resolution exhausted the anonymous GitHub rate limit and closed the `ConfigEval` gate. Exit: either a rendered baseline pin with a named update path, or a recorded decision that a released tool resolves live and the drift is the user's to pin through their lock.

## Q-014 — How does a released vivarium supply its own guest module and supervisor to a generated flake?

Slice 012 made the generated flake carry a third baseline input beside `nixpkgs` and `microvm`: the product flake itself, which publishes the guest module, its build inputs, and the launch seam that renders a launch specification from a resolved guest config. Development pins it to this working tree through `VIVARIUM_BASELINE_VIVARIUM`, which is the same seam and the same convention the other two already use. The shipped default is a branch reference, and that is the part nobody has decided: a released tool naming its own repository by branch resolves upstream on every fresh evaluation, and pinning it instead creates an obligation to move the pin whenever the supervisor changes — a version skew between the `viv` a user runs and the supervisor their guest was built against. This parallels [`Q-009`](#q-009--does-the-generated-flake-carry-a-baseline-pin-for-its-own-inputs) and is the sharper form of it, because the two halves here are one program. Blocks: [slice 015](slices/015-the-binary-supplies-itself/README.md), whose item 1 is this decision. Raised: composing the guest module into the generated flake. Exit: the ADR slice 015 records — the binary carries the product tree and supplies it to every preparation, so the input, and with it the choice between a branch and a pin, ceases to exist — or a recorded decision refusing that shape.

## Q-010 — How does the supervisor publish the descriptor limit the contract asserts?

The limit is spelled six times across a boundary Nix cannot cross: `524_288` in [`spec.rs`](../../src/launch/spec.rs), and `524288` in [`policy.rs`](../../src/launch/policy.rs), [`systemd.rs`](../../src/launch/systemd.rs), [`launch-arguments.nix`](../../nix/launch-arguments.nix), [`contract.sh`](../../tests/nix/contract.sh), and [`first-microvm-check`](../../tests/host/first-microvm-check). Nothing derives one from another, so the contract's assertion is a literal restated rather than two independently realised artifacts compared — the defect that file's own header exists to avoid. Blocks: eliminating the last literal-only cross-boundary assertion. Raised: ADR-0098's deferred gap. Exit: a supervisor introspection subcommand that emits its constants, which the contract then diffs against the launcher JSON.

## Q-012 — Which command enforces N24, and can it be enforced before launch at all?

Nothing checks it. [`../../src/config/merged.rs`](../../src/config/merged.rs) classifies the N11 literal-path half of a shared layer's mount sources, and the session-directory half — a `source` resolving to `/tmp`, `/var/tmp`, `${XDG_RUNTIME_DIR}`, or an ancestor of one — has no classifier anywhere. Unlike N11 it may not be decidable from artifact text: the sources it forbids are named by a host variable that resolves at launch, so a merged-configuration check could only catch the literal spellings. Blocks: nothing today, because no launch path consumes a mount yet; slice 012's mount construction is where it stops being theoretical. Raised: reviewing item 5. Exit: either a classifier in the merged view for the decidable spellings plus a launch-time check for the rest, or a spec line placing the whole invariant at launch.

## Q-013 — Can `config sources` report an irreconcilable merge?

[`01-command-surface.md`](../reference/spec/01-command-surface.md) fixes `conflicts` at two kinds, `tie` and `literal-path`, so a duplicate volume name — spec/14's own cited instance of an irreconcilable merge — has nowhere machine-readable to go. `viv config eval` refuses it with `65` as specified, and the provenance view a user reaches for next reports nothing about it. Widening the vocabulary is the obvious fix and is exactly the kind of change the two-field entry was kept narrow to avoid. Blocks: nothing in flight; it is a gap in the pair's division of labour rather than a defect in either half. Raised: reviewing item 5. Exit: either a third `kind` with the trial that reads it, or a spec line saying an irreconcilable merge is `config eval`'s to report alone.

## Q-015 — May `viv status` report `resources` as `null` for a running VM whose launch specification is unreadable?

Raised as one question with the `failed` reason vocabulary, and narrowed once that half was settled: the reason set is open by specification, a consumer is obliged to tolerate a value it does not recognize, and vivarium therefore adds one reason per condition it can tell apart, which is an additive change needing no decision. This half is the opposite kind of change and is why the two separated. [`declared_resources`](../../src/cli/lifecycle.rs) reads the ceiling in force back out of the launch specification, and substitutes a shipped floor when that file cannot be read or parsed — operational data derived from no running VM. The obvious repair is unavailable twice over: `mem_mib` is an integer, and no integer means unknown, so the only non-committal value is `null`; and [`01-command-surface.md`](../reference/spec/01-command-surface.md) guarantees the field is never `null` while the VM runs, which is a promise a consumer may already read the field unconditionally on. Nor can the condition be reported as `failed` and carry a reason, because a VM with a live process and an active unit is genuinely running and `stop` and `exec` still reach it — only the bookkeeping is broken. Blocks: nothing running; a consumer reading `resources` cannot distinguish a measured ceiling from a constant. Raised: the second review round of slice 012. Exit: either an `01-command-surface.md` amendment admitting `null` for the unreadable-record case, carrying the compatibility note that retracting the guarantee implies, or a recorded decision that the shipped floor is the reported ceiling and the guarantee stands unchanged.

## Q-016 — How does a linked worktree reach its main repository inside the guest?

The host-symmetric mount (ADR-0100) is necessary for git's linked worktrees and not sufficient for them. A linked worktree's `.git` file names `<main-repo>/.git/worktrees/<id>`, which lies outside the one directory vivarium shares, so a bound worktree mirrors at the right path and still has no resolvable git directory. The intended route is the declared-mount surface — a user names the main repository's git directory as a mount whose `source` and `target` are the same host path — and that surface is inert: [`../reference/spec/06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) specifies it, [`../../nix/vivarium-options.nix`](../../nix/vivarium-options.nix) types it, [`../../src/config/flake.rs`](../../src/config/flake.rs) emits it, and nothing consumes it, because [`../../nix/guest.nix`](../../nix/guest.nix) and [`../../nix/launch-arguments.nix`](../../nix/launch-arguments.nix) each hardcode exactly two shares. Blocks: nothing in flight; slice 014 mirrors the path and leaves the worktree case named rather than served. Raised: adopting path symmetry in slice 014 item 1. Exit: either declared mounts reaching `microvm.shares` so a user can serve their own main repository, or a recorded decision that vivarium derives that share itself when the bound project is a linked worktree.

## Q-017 — Should the guest home move out of `/home`?

The guest user's home is `/home/vivarium` ([`../../nix/guest.nix`](../../nix/guest.nix)) and it is an ext4 volume, so it is the one guest-owned path that a mirrored host path can plausibly collide with: a host user named `vivarium` keeps their projects under exactly `/home/vivarium`. ADR-0100 refuses that case rather than mounting into a user's persistent home, which is correct and is also a limitation with no workaround the user can apply. Moving the guest home to a path no host user can occupy would remove the collision entirely, but the home path is build-channel and spec-visible — [`../reference/spec/06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) says the default volume mounts at the guest user's home — so it is a decision rather than a rename. Blocks: nothing; the refusal is safe and named. Raised: enumerating ADR-0100's refusal set. Exit: either a decision moving the guest home with the volume mount point and first-boot seeding following it, or a recorded decision that the refusal is the permanent answer.

## Q-018 — How does `viv stop --timeout` reach the supervisor that owns the graceful rung?

[`10-vm-lifecycle.md`](../reference/spec/10-vm-lifecycle.md) gives the operator a grace period and says `-1` waits indefinitely, and the flag is fully honoured on the host side: [`grace_seconds`](../../src/cli/lifecycle.rs) turns it into the deadline `stop_unit` polls to before it reaches for `systemctl kill`. The rung it is meant to bound is somewhere else. Powering the guest down is the supervisor's, and the supervisor was started by `viv start` — it raises the ACPI power button, waits [`GUEST_POWEROFF_TIMEOUT`](../../src/launch/supervisor.rs), and destroys the VM, with nothing carrying the stop-time value across to it. So `--timeout 30` and `--timeout -1` both buy a longer wait before the group is killed and the same six seconds before the guest is destroyed, which is the opposite of what the flag is for: the point of asking for longer is to let a slow guest finish committing. Widening the constant is not available as a repair, because the ladder has to fit inside the ten-second default when no flag is given. Blocks: nothing in flight; slice 014 item 3 fixed the durability defect the default grace was losing writes to, and the flag's reach is a separate half. Raised: the first review round of slice 014. Exit: either a launch-time channel that carries the requested grace to the running supervisor before its cancellation path runs, or a recorded decision that the graceful rung is bounded by the shipped default and `--timeout` bounds only the hard one, with `10-vm-lifecycle.md` amended to say so.

## Q-019 — Should a non-UTF-8 project path be carried to the guest, or refused?

N16 promises the project is reachable by one absolute path string on both sides, and a Unix path is bytes, so a project directory holding a byte that is not valid UTF-8 is a case the promise covers by wording and not by behaviour. [`encode_cmdline_path`](../../src/launch/supervisor.rs) is byte-exact and its unit test proves it, but the launch specification reaches that function as JSON: [`../../nix/runner.sh`](../../nix/runner.sh) injects the workspace path with `jq --arg`, and a JSON string is Unicode, so the byte has already become U+FFFD. The guest is then mirrored at a path that differs from the host's in exactly the way ADR-0100 exists to prevent, and nothing reports it — validation inspects the substituted path, which either exists and is the wrong directory or does not exist and fails as `ENOENT` naming a path the user never typed. The encoder is not the place to fix it, because by then the information is gone. Blocks: nothing; the case is rare and the failure is loud more often than silent. Raised: the second review round of slice 014, from a test that proved the encoder and read as proving the pipeline. Exit: either the workspace path crossing the JSON boundary in a byte-preserving encoding, or a refusal at the boundary that names the path as unmirrorable for the same reason the guest-owned paths are, so a user meets a diagnostic rather than a wrong directory.

## Q-020 — What raises a volume's ceiling once its image exists?

[`06-workspace-and-project-environment.md`](../reference/spec/06-workspace-and-project-environment.md) says a volume's ceiling may be raised between boots and never lowered in place, which reads as a promise a user can act on by editing `size_gib` and restarting. Nothing performs the raise. [`provision_volumes`](../../src/launch/supervisor.rs) creates an image only when none is there, so a larger declaration reaches the launch contract and the guest keeps the filesystem its first boot was given; `viv volume list` then reports the image's own length, which is the ceiling actually in force rather than the declared one, so the two views do not contradict each other and nothing is reported as wrong. Growing it is not a line: the file has to grow and then the filesystem inside it, which needs `resize2fs` in the backend program set and a decision about whether the check it wants runs first. Blocks: nothing in flight; a user who outgrows a volume today recreates it by removing the image. Raised: a review round of slice 014 items 4 to 6. Exit: either an offline grow step before attach, with the program set and the failure code it answers on, or a spec amendment saying a ceiling binds at creation and a raise takes effect only for an image that does not exist yet.

## Q-021 — What is the `--json` record for `viv stop` and `viv destroy`?

[`10-vm-lifecycle.md`](../reference/spec/10-vm-lifecycle.md) binds both verbs in one sentence — empty stdout on success, one record under `--json` — and no page fixes that record's shape, unlike every data command whose fields [`01-command-surface.md`](../reference/spec/01-command-surface.md) enumerates. Neither verb emits one, so `viv stop --json` and `viv destroy --json` succeed with zero bytes on stdout and a caller that selected machine mode gets nothing to parse. Inventing a shape from inside either verb would settle a two-command contract from one side, and the two have different things to say: a stop reports which rung of the ladder ended it, while a destroy reports what it removed and what it spared, which is already a value the prompt renders. Blocks: nothing in flight; both verbs are scriptable on their exit code today. Raised: a review round of slice 014 items 4 to 6. Exit: either one `01-command-surface.md` entry fixing both records' fields, with the verbs rendering them, or a spec amendment withdrawing the `--json` record for side-effect verbs and leaving the exit code as the machine-readable result.

## Q-024 — What stops a sandbox whose trial process never ran its own cleanup?

[`TempProject`](../../tests/support/mod.rs) already answers the ordinary case, and its own comment records the measurement that forced it: a detached start outlives the process that submitted it, `systemd-run --collect` reaps only an inactive unit, so a trial that starts a VM and never stops one leaves it running. The repair is `stop_leaked_vms` in `Drop`, selecting units by the runtime directory in their own command line so a developer's own sandbox is never matched. What `Drop` cannot cover is the process not finishing: a trial killed by a harness timeout or a signal never runs it, and nothing else sweeps, because cleanup lives in the test process and no runbook under [`../../tests/host/`](../../tests/host/) looks for a stranded unit. Observed on 2026-08-13: three `vivarium-shell-project-t*` units from the 2026-08-12 run were still active twenty-seven hours later, each holding a live `cloud-hypervisor` process and roughly 0.4 GiB, all three from `workflow_06_shell` — the one trial driving a real terminal, and so the one most likely to be killed rather than to return. Blocks: nothing in flight; the units are stopped by hand once seen, and distinct project ids mean the next run does not collide. Raised: inspecting the host while hand-running slice 014's `Done when`. Exit: either a sweep the host runbooks call before and after a capable-host run, keyed on the same command-line match `Drop` uses, or a recorded decision that an interrupted run is the operator's to clean up, said where the operator reads it.

## Q-023 — What keeps a store collection from deleting a project's current build?

[`02-config-and-xdg-layout.md`](../reference/spec/02-config-and-xdg-layout.md) has each project's state hold a Nix profile whose numbered symlinks pin retained build outputs as garbage-collector roots, and [`10-vm-lifecycle.md`](../reference/spec/10-vm-lifecycle.md) has `destroy` unlink them. Slice 014 already records that the unlink is a no-op because that profile does not exist yet. The other half is that nothing creates a root either: `last-build` is a file holding a store path as text, which nothing in Nix follows, so a project's build is reachable from no root at all. Measured on 2026-08-14 while clearing the host: `nix-store -q --roots` on this repository's own `vivarium-first-microvm` returned nothing and the path was in the dead set, so an ordinary `nix-collect-garbage` would have taken a 4.5 GiB closure that a start otherwise reuses in about twenty seconds — the difference between an evaluation and the roughly twenty-nine minute build behind it. Nothing announces the loss beforehand and the next `viv start` succeeds, so it is read as a slow day rather than as a collected store. Blocks: nothing in flight; a hand-added root under the user's own `gcroots` covers a machine where it matters. Raised: cleaning the host after hand-running slice 014's `Done when`. Exit: either the per-project profile of [`11-generations-and-build-history.md`](../reference/spec/11-generations-and-build-history.md) rooting each retained build as it is produced, which is also what gives `viv gc` something to sweep, or a recorded decision that vivarium roots nothing and a store collection costs a rebuild, said where a user reads it rather than discovered afterwards.

## Q-025 — Should the pair's input hook be default-deny rather than unfiltered?

The allowlist's enforcement lives entirely on the forward hook: [`base_ruleset`](../../src/net/nft.rs) filters what the guest sends through the tap toward the uplink, while traffic delivered locally to the namespace's own addresses takes the input hook, which the table leaves unfiltered. The safety argument is that the gating resolver is the namespace's only listener, so the open input path admits exactly guest-to-resolver DNS — but that is a property of what the supervisor happens to spawn, not a rule the kernel enforces. Any later process joined into the pair with a listening socket — a widened uplink, a debugging tool left behind, a fixture that outlives its trial — becomes guest-reachable with no rule changing and nothing failing, which is how an enforcement gap arrives silently. Blocks: nothing in flight; today's process set makes the property true, and the trials that would notice a second listener ([`tests/user_workflows.rs`](../../tests/user_workflows.rs) probes the resolver socket from inside the pair) observe the process set, not the policy. Raised: reviewing slice 004's merged pass, where removing the forward chain's inert DNS-accept rule surfaced that guest DNS reaches the resolver over the input path. Exit: either an input chain in `base_ruleset` admitting established flows and guest-to-resolver DNS with the same reject-not-drop tail the forward chain carries, or a recorded decision that the single-listener property is the guarantee, with the comment on `base_ruleset` naming it load-bearing.

## Q-026 — What distribution should size the agent-startup budget?

[`AGENT_STARTUP_TIMEOUT`](../../src/launch/supervisor.rs) bounds the rung a `viv start`'s wall clock is dominated by — guest boot to the agent answering on the control socket — and its 20s value is interim: sized as roughly 2.3x one host's ~8.5s end-to-end boot figure, after the previous 10s (a ~1.2x margin) expired twice in one day under host load. Two failures and one end-to-end figure are evidence of possibility, not a distribution, and the constant's comment says so. The launcher-side repair already landed — a failed launch reports through the readiness socket before teardown, so the operator no longer waits out the launcher's 30s to learn nothing — which makes this a calibration question rather than a defect. Blocks: nothing in flight; a budget miss now fails fast with the rung named in the journal. Raised: diagnosing `workflow_01_first_time_bind_boot` failing pre-push twice on 2026-08-14, where the supervisor's journal named `timed out waiting for guest agent` while the CLI reported the launcher's 30s. Exit: either a per-rung measurement — `vm.boot` issued to `wait_for_agent` returning, ten boots idle and ten under load resembling the observed pressure — fixing the constant from the distribution with the derivation beside it, or a recorded decision that the agent rung takes the launcher's budget minus reporting headroom and tracks it structurally.

## Q-027 — What detects a launch-schema skew the runner's argument contract cannot see?

A generated flake pins its own `vivarium` input, so the runner a project builds comes from the snapshot its retained lock names while the `viv` a user runs comes from wherever that binary came from — the skew [`Q-014`](#q-014--how-does-a-released-vivarium-supply-its-own-guest-module-and-supervisor-to-a-generated-flake) weighs when it asks whether a released tool should pin itself. Half of it is already guarded: [`../../nix/runner.sh`](../../nix/runner.sh) refuses an argument name an older launcher does not know, names the launch contract's own `schemaVersion` while doing so, and does it before any specification is written. The other half has no guard, because a schema bump need not touch an argument name. Measured on 2026-08-14 while hand-running slice 014's coding-agent clause: schema 6 added networking fields to the launch record and changed no argument, so a runner built from a schema-5 snapshot accepted every argument, wrote a schema-5 record, and execed the `viv` its own build pinned — which validated it and launched the supervisor it matched. `viv start` reported success and `viv status` reported `running`, both truthfully, against a record no verb built from the newer tree could read; the first `viv exec` then failed `vm.launch-record-unreadable`, whose `why` names the schema and not the stale pin behind it. Blocks: [slice 015](slices/015-the-binary-supplies-itself/README.md), which removes the cause and adds the named refusal; until it lands, deleting the project's retained `flake.lock` so the next evaluation writes a new one clears an instance by hand. Raised: hand-running slice 014's `Done when` against a tree that had moved since the project's lock was written. Exit: slice 015's ADR and its pre-boot schema comparison, refusing before boot with both versions named — or a recorded decision that refreshing a project's lock is the operator's job and a session verb's refusal is where the skew is meant to surface.
