# vivarium documentation

Index into the project's four documentation zones. Each zone is a reader promise, not a topic bucket. This page is only an index — it holds no canonical facts of its own.

## Zones

- **[`reference/spec/`](reference/spec/README.md)** — the **product contract**: what vivarium is and does. Goals and non-goals, the command surface, the XDG config layout, the image/piece/manifest artifact model, composition and determinism, networking and egress, the workspace and inner project environment, secrets and config sharing, the normative invariants, the glossary, and the resource-and-capacity model that lets several sandboxes share one host.
- **[`decisions/`](decisions/)** — lean ADRs recording the durable _why_ behind the architecture: the isolation boundary, the module system as the composition engine, the artifact model, the manifest format, the config layout, manifest binding, egress policy, layer separation, workspace path handling, secrets, config being read-only to the tool (binding in state), generating config examples from types, the VM lifecycle and `viv start` semantics, build generations pinned as GC roots, the CLI output-and-failure contract, guest control transport and exec/shell exit boundary, the workspace mount path plus extra mounts, the lifecycle verbs and stop/destroy teardown boundary, the persistent volume model, the mount/config-mirroring schema, the CLI implementation baseline (the dependency choices, error/exit-code realization, and the logging stack), the elastic-resource set (guest memory as a ceiling, host scoping and admission control, sparse volumes, guest store sharing, and share cache policy), the sharing boundary that keeps the manifest personal while images and pieces carry a team's guarantees, the per-option classification that puts resource ceilings on the launch channel and volumes on the build channel, the rule making an evaluation-time content defect a hard error that the provenance viewer still renders, the identity marker's lifecycle across `start` and `destroy`, host-side egress enforcement with fail-fast denials, how a bare identifier in a manifest resolves to a file in the config library, the global config file and the precedence chain it sits in, the choice to give the manifest no schema version, the split that takes only guest-side system configuration from upstream while vivarium owns the launch itself, the rule that makes the virtualization backend a member of the built closure rather than a host dependency to be probed, the on-disk layout of the state root's own files and which part of it is public contract, how those files are written and locked against concurrent processes, the rule that a binding whose project directory has vanished is surfaced rather than quietly reaped, the decision to require a runtime directory rather than synthesize one when the host does not supply it, the session boundary that follows from it — a VM's lifetime ends with the user's login — the closed manifest key table and the parse-versus-evaluate line that keeps one defect from carrying two exit codes, the generated flake as a materialized cache artifact whose store-input nature reaches the manifest's own text, the tool-owned per-target lockfile that finally gives determinism a file to name, the ruling that `extends` is one local module and never inheritance of another manifest, the rule that what vivarium ships is examples to copy rather than a second namespace names resolve against, the scoping of a team's override lock to one manifest and the refusal that follows for `viv update`, the directory manifest form `extends` requires so the copied unit never reaches the rest of the library, the rule letting a shared image or piece declare its own third-party flake input and the refusal that follows when the effective lock carries no node for one, the pre-1.0 promise that makes the minor component the breaking axis, the test lanes and the technique for proving an absence rather than scanning for one, the process by which a backend advisory becomes a released pin move, the single-maintainer form that process takes, the disposability of a sandbox — which turns guest-side durability into a non-goal as a class — the guest-side rule that keeps the console channel lossless by writing to the console device rather than through the guest's log daemon, the metric on which a guest's returned memory is actually measured, the ruling that the project's inner environment provisions its own store rather than borrowing validity from the host's, which is what keeps vivarium agnostic about a host it may assume nothing about, the garbage-collection root a running guest takes over the store paths it reads, the standing refusal of a per-VM store copy, which would make several sandboxes cost more disk than the container model rather than less, the volume that carries the guest's own writable store layer so a package installed inside a sandbox is still there after a restart, and the store type that makes collecting garbage inside a guest safe rather than something that quietly blinds it to the share it reads. `template.md` is the drop-in ADR shape.
- **[`reference/`](reference/)** — lookup material beyond the spec: [`implementation-status.md`](reference/implementation-status.md) is the single source of truth for what works today versus what is designed only, and carries the pre-1.0 stability promise; [`testing-lanes.md`](reference/testing-lanes.md) is the lane taxonomy — what each test lane proves and which are required; [`microvm-verification-harness.md`](reference/microvm-verification-harness.md) documents `scripts/first-microvm-check`, the hand-run harness that boots the first microVM on a real host, and carries the register of what has actually been verified there.
- **[`guides/`](guides/)** — task walkthroughs: [`getting-started.md`](guides/getting-started.md) walks the intended end-to-end flow, and nine per-task how-tos follow it — the eight that each pair with an acceptance trial encoding the same sequence, plus the secrets walkthrough noted below. Getting a project running: [`first-time-bind-boot.md`](guides/first-time-bind-boot.md) binds a manifest and boots for the first time, [`clean-repo-global-registry.md`](guides/clean-repo-global-registry.md) does it without putting anything in the repository. Shaping what the VM contains: [`team-shared-personal-overrides.md`](guides/team-shared-personal-overrides.md) layers a personal override over a team-shared config, [`inspect-before-run.md`](guides/inspect-before-run.md) reads the merged result before anything boots, [`restrict-egress-allowlist.md`](guides/restrict-egress-allowlist.md) narrows network access to a named list. Working and tearing down: [`run-agent-command.md`](guides/run-agent-command.md) runs a command in the guest and gets its exit status back, [`stop-restart-preserving-volumes.md`](guides/stop-restart-preserving-volumes.md) stops and resumes without losing work, [`destroy-cold-rebuild.md`](guides/destroy-cold-rebuild.md) tears a project down to a clean first run. Handling credentials: [`keep-secrets-out-of-the-store.md`](guides/keep-secrets-out-of-the-store.md) walks each safe channel in turn — agent forwarding, a token passed at launch, a read-only credential mount, and the user-owned encrypted-at-rest shape — and is the one guide that pairs with no trial of its own, because the rule's decisive half is not decidable by inspection.
- **[`explanation/`](explanation/)** — the mental model: [`architecture.md`](explanation/architecture.md) explains the sandbox-vs-project-environment split and how the pieces fit together; [`disk-model-vs-containers.md`](explanation/disk-model-vs-containers.md) explains why running a fifth sandbox costs so little disk, comparing the store's sharing unit against a container image's layer stack, and why the writable shared store that container tooling gets away with is refused here.
